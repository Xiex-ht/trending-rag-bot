### 已扫清的障碍（排障实录，面试可讲的细节）

1. **镜像拉取失败（Dify weaviate）**：compose 声明的 `cr.weaviate.io` 域名被引擎丢弃、回退 Docker Hub，而 Hub 域名解析到 DNS 污染的 IPv6 地址导致超时。解法：改从可用通道 `docker pull semitechnologies/weaviate:1.39.2`，再 `docker tag` 打回原名字，compose 直接用本地镜像。
2. **LangBot 镜像同样拉不到**：GitHub 直连不通（故改用加速代理下载仓库 zip）；官方国内源 `docker.langbot.app` 亦不可达。解法同 1：从 `docker.1ms.run` 拉取 + `docker tag` 恢复原名后启动。
3. **LangBot Box 沙箱启动失败**：其卷挂载路径含 Windows 盘符冒号，被 Docker Desktop 拒绝。处置：以 `BOX__ENABLED=false` 关闭沙箱，聊天链路不受影响；后续若需插件/技能执行再单独解决。
4. **`Workflow not published`（400）**：应用未点"发布"，Dify 拒绝对外提供草稿态服务。解法：编排页右上角发布。
5. **回复中泄漏 `think` 段**：根因是接入的模型为混合思考架构（推理通道独立于正文，提示词无法约束）。解法：Dify 应用模型参数中关闭 `enable_thinking`，或改用无思考形态的模型（如 `qwen-plus`/`deepseek-chat`）。
6. **cmd 批处理中文编码连环坑**：中文目录（`Desktop\code\代码`）+ 中文文件名（`爬虫.py`）在 bat 中被 GBK/UTF-8 反复转码，先后出现注释乱码报错、找不到文件、甚至误执行同目录另一中文脚本。终解：bat 只按 ASCII 文件名调用中间启动器 `weekly_crawler_launcher.py`，由 Python 在运行时按内容标记（`TRENDING_URL`）定位真正的爬虫——Python 处理中文路径无编码问题，链路验证 `exit=0`。
7. **IDE 报 requests/bs4 未解析**：非缺库，是 IDE 选的解释器与命令行实际使用的 Anaconda 环境（`D:\anaconda`，包齐全）不一致，纯编辑器静态分析问题，不影响运行；把 IDE 解释器指向 Anaconda 即可消除。
8. **任务计划程序"为任务运行输入密码"报错**：选择"不管用户是否登录都要运行"需验证密码（且只认账户密码不认 PIN）。处置：改用"只在登录时运行"，配合"错过补跑"设置达到同等效果；已用 `Set-ScheduledTask` 开启 `StartWhenAvailable` 与电池模式可运行并验证生效。

## 一、任务 1：基于 Dify + LangBot 制作企业微信聊天机器人

### 1.1 可行性结论：高度可行

技术链路：

```
企业微信用户(群聊@/单聊)
      │  WebSocket 长连接（无需公网IP/域名/备案/SSL）
      ▼
   LangBot（消息适配层，Docker 部署，WebUI :5300）
      │  HTTP 调用 Dify 应用 API（/v1/chat-messages）
      ▼
   Dify（AI 大脑：知识库 RAG + 提示词 + 工作流）
      │
      ▼
   模型供应商（通义/DeepSeek/OpenAI 兼容接口等）
```

### 1.2 关键依据（均经联网核实，2026-09）

1. **LangBot 官方支持企业微信**：README 明确列出支持 QQ、微信、企业微信、飞书、钉钉、Discord、Telegram 等平台，并"深度适配 Dify"，是官方主打的 LLMOps 集成场景。
2. **企业微信智能机器人支持 WebSocket 长连接 API 模式**：由开发者服务（LangBot）主动向企业微信发起 wss 连接，配 Bot ID + Secret 即可，**不需要公网 IP、域名、SSL 证书、ICP 备案**。这是本地笔记本部署能跑通的根本原因。
3. 已有 2026 年公开实战教程验证"Dify 知识库 → 企微智能机器人 → LangBot → WebSocket"全链路（含群聊问答场景）。

### 1.3 两种企微接入方式对比

| | 智能机器人（WebSocket，推荐） | 自建应用（回调 URL） |
|---|---|---|
| 公网要求 | 无 | 需公网 HTTPS 域名 + 备案 + IP 白名单 |
| 本地部署可行性 | 直接可行 | 需内网穿透，稳定性差 |
| 能力 | 单聊/群聊@、流式输出 | 工作台入口、消息推送、 richer API |
| 门槛 | 企微管理员在后台创建机器人 | 企微管理员创建应用 |

**唯一硬前提**：你需要企业微信管理员（或可管理"智能机器人"的子管理员）权限。没有企业或拿不到权限时，可先用 LangBot 支持的其他渠道（如 Telegram/Web 测试页）验证链路，方案不变。

### 1.4 实施步骤（预估 1~2 天跑通）

**Step 1 · Dify 侧准备**
1. 创建知识库，上传初始文档（先用 10~20 篇验证）；
2. 创建 Chat 应用（对话型），关联知识库，配置模型供应商 API Key；
3. 点击"发布"→ 访问 API → 生成 `app-` 开头的 API Key；
4. 用 curl/Postman 先本地调通 `/v1/chat-messages`（确认知识库检索返回正常）。

**Step 2 · 企业微信后台**
1. 登录 work.weixin.qq.com 管理后台 → 管理工具 → 智能机器人 → 创建机器人；
2. 选择 API 模式，连接方式选 WebSocket 长连接；
3. 记录 Bot ID 与 Secret。

**Step 3 · 部署 LangBot**
```bash
docker run -d --name langbot \
  -p 5300:5300 \
  -v ./data:/app/data \
  langbot/langbot:latest
# 或官方 compose 方式；首次访问 http://localhost:5300 设置管理员账号
```
注意：容器内访问宿主机 Dify 用 `http://host.docker.internal/v1` 作为 endpoint。

**Step 4 · LangBot 配置流水线**
1. 新增"机器人"：平台选 企业微信智能机器人，连接方式 WebSocket（关闭 Webhook 开关），填 CorpID/Bot ID/Secret；
2. 新增"流水线（ChatPipeline）"：机器人适配器选上一步的企微机器人，AI 服务选 **Dify**，填 API Key 与 endpoint；
3. 启动机器人，状态显示"已连接"即成功。

**Step 5 · 联调与边界测试**
- 单聊问答、群聊@问答、连续多轮（会话隔离）、长回复流式截断、图片消息、超时重试；
- 已知坑：旧版 LangBot 企业微信智能机器人 + Dify chatflow 有 500 报错的 bug（issue #1715），**部署 latest 版本规避**；另一常见坑是企微消息回调里 `sender_name` 显示为企业 ID 而非用户名（v4.9.4 已修复，同样保持版本最新）。

### 1.5 风险清单

| 风险 | 等级 | 应对 |
|---|---|---|
| 无企微管理员权限 | 高（阻塞） | 申请权限，或先用其他渠道验证链路 |
| 本地电脑关机 → 机器人离线 | 中 | 简历场景可接受；生产场景后续迁移到云服务器 |
| 模型 API 费用 | 低 | 免费额度模型起步（如 DeepSeek/通义新用户额度） |
| LangBot 与企微 API 变更 | 低 | 跟随官方版本更新 |

### 1.6 平台选型调整：QQ 官方机器人（路线 A，2026-09-25 确认采用）

三条平台路线核实结论：

| 路线 | 合规性 | 公网要求 | 群聊 | 前置门槛 | 结论 |
|---|---|---|---|---|---|
| 企微智能机器人 | ✅ 官方 | 无（WebSocket） | ✅ | 需企微管理员权限 | 保留为第二渠道 |
| **QQ 官方机器人** | ✅ 官方 | 无（沙箱阶段） | ⚠️ 正式环境需审核 | QQ 实名即可 | **当前主路线** |
| QQ 个人号（NapCat 等） | ❌ 违反协议、封号风险 | 无 | ✅ | QQ 小号 | 不采用，不写入简历 |

QQ 官方路线要点：
- 注册：q.qq.com 个人开发者实名创建机器人，取 AppID + AppSecret（Token 字段新版已弃用）；
- 沙箱限制：仅支持单聊，测试成员需手动添加；群聊与 IP 白名单是正式环境的门槛，本机阶段不做；
- LangBot 三个配置开关：Webhook 关（走 WebSocket）、流式回复开、Markdown 渲染开；
- **多渠道路径**：LangBot 流水线与机器人解耦，同一 Dify 应用可同时挂企微 + QQ，简历表述升级为"一套大脑、多端交付"。

**已完成**：LangBot 侧 Dify 流水线跑通、WebUI 配置项确认。**下一步**：开放平台注册与沙箱验证。

## 二、任务 2：RAG 优化 + 文档定时更新 + 提示词工程

### 2.1 可行性结论：可行，且是本项目含金量最高的部分

Dify 1.17.1 原生具备以下能力（无需二次开发平台）：
- 知识库分段：自定义分隔符、分段长度/重叠、**父子分块（层次分段）**；
- 检索：向量检索 / 全文检索 / **混合检索**、**Rerank 重排序**、TopK 与 score 阈值、元数据过滤；
- 知识库 API：外部程序以编程方式创建/更新/删除文档（定时同步的基础）；
- Dify ≥1.10 内置**触发器（Trigger）**：工作流可被 webhook/定时事件唤醒；
- 日志与标注：线上问答记录可人工标注对错，构成评测集来源。

### 2.2 四条子路线

**A. 文档定时更新入库（Webhook 方案）**
```
文档源(企微文档/微盘/共享目录/Git)
   │ 变更通知(webhook) 或 定时轮询
   ▼
同步脚本(Python)：下载/检测变更 → 调 Dify 知识库 API
   POST /datasets/{id}/document/create-by-file（新文档）
   POST /datasets/{id}/documents/{doc_id}/update-by-file（覆盖更新）
   ▼
Weaviate 索引自动更新 → 机器人即刻可答新内容
```
- 定时层：Windows 计划任务 / cron / Dify 工作流定时器均可；
- 进阶加分项：文档版本号与删除同步（避免旧文档残留污染检索）。

**B. 分块算法优化（做对照实验）**
- 基线：默认通用分块（500 tokens / 重叠 50）；
- 对照组 1：按文档结构分块（Markdown 标题层级 / QA 对）；
- 对照组 2：父子分块（子块召回、父块投喂，兼顾精准与上下文完整）；
- 记录每组在测试集上的检索命中率差异 → 这就是简历里的量化数据。

**C. 检索链路优化**
- 混合检索（向量+关键词）解决"专有名词/编号类"查询召回差的问题；
- 接 Rerank 模型（bge-reranker 经硅基流动等免费 API，或本地 Ollama）；
- 调 TopK（3→5→8）与 score 阈值，观察引用质量。

**D. 提示词工程**
- 系统提示词约束："仅依据上下文回答/不知道就说不知道/标注来源文档"，抑制幻觉；
- 上下文模板与引用归属设置；
- 问题改写（query rewrite）：多轮对话中把"它多少钱"补全为完整问题再检索。

### 2.3 评测方法（简历数字的来源，强烈建议做）

1. 构造 30~50 条真实问题测试集（问题 → 标准答案 → 答案所在文档）；
2. 写一个小 Python 脚本批量调 Dify 应用 API，记录：检索命中率、答案正确率（人工判或 LLM-as-judge）、平均延迟；
3. 输出对比表：基线 vs 分块优化 vs 检索优化 vs 提示词优化 vs 全部叠加；
4. 典型可达成效果参考（社区普遍经验，以你实测为准）：混合检索+rerank 可将封闭域问答准确率从 ~70% 提升到 ~90%。

### 2.4 知识库构建方法（前置：先建库，才有可优化的对象）

**选题原则**：挑自己熟悉、问答需求真实的领域（专业科目 / 行业资料 / 某产品完整文档），起步 30~100 篇（10~50 万字）即可验证效果。

**优质数据优先级**：FAQ 问答对 ＞ 操作手册/SOP ＞ 政策制度条款 ＞ 领域文章教程 ＞ 会议记录/聊天记录（结构差，少用）。避开表格图片密集、扫描版 PDF、超长无标题文档。

**五步流程**：
1. **预处理**（占 60% 价值）：转 Markdown、一篇一主题、清页眉目录噪音、缩写给全称；
2. **建库**：Dify 知识库上传 → 分段先用默认通用分块跑**基线**（对照实验需要它）→ 处理完**逐篇检查切片**，看有无句子拦腰切断；
3. **关联应用**：应用编排 → 上下文挂知识库 → TopK 3、score 阈值 0.5 起步 → 重新发布；
4. **构造评测集**：30~50 条"问题+标准答案+出处文档"，作为后续一切优化的考卷；
5. **迭代**：看 Dify 对话日志的召回段落做归因（没检到 / 检错段 / 模型没用好），再决定动分块、检索还是提示词。

### 2.5 知识库自动化管道落地记录（2026-09-25，路线 A 的"半程版"已上线）

原路线 A 的文档源是企微文档/微盘（受权限限制暂不可用），实际落地改用 **GitHub 周榜**作为自动化素材源，跑通"定时抓取 → 结构化入库素材"的前半程：

```
Windows 任务计划程序（每周一 09:00，错过补跑、电池可运行）
   ▼
每周爬取.bat（纯 ASCII，只调用英文文件）
   ▼
weekly_crawler_launcher.py（按内容标记 TRENDING_URL 定位中文名爬虫，绕开 cmd 中文编码坑）
   ▼
爬虫.py：requests+bs4 抓 github.com/trending?since=weekly Top10
   → GitHub REST API 补 topics/默认分支
   → raw.githubusercontent.com 抓各仓库 README 并清洗成 ~500 字摘要
   ▼
Desktop\agent\github-trending\  11 个 UTF-8 Markdown（10 详情 + 1 汇总，文件名 01-xxx.md）
Desktop\agent\run.log  运行日志（每次 START/DONE + 退出码）
```

**产出物结构**（为 Dify 父子分块设计）：每个项目 MD 含 `## 基本信息`（表格：语言/Star/本周新增/Topics）、`## 项目简介`、`## README 摘要` 三节；汇总表含榜单全览与语言分布统计。

**关键工程决策**（面试可讲）：
- 网络探测先行：直连/代理/镜像站三通道逐一测活再选型（当日直连恢复可用，脚本预留 `--proxy` 参数位随时切换 Clash 等代理）；
- README 抓取多分支多文件名降级尝试（main/master × README.md/readme 等 7 种组合），首次实跑 10/10 全部成功；
- cmd 中文编码问题的架构级解法：调度层全 ASCII，中文路径解析下沉到 Python 运行时。

**剩余半程**：手动上传 11 个 MD 进 Dify（当前）→ 追加 `sync_to_dify()` 直调知识库 API 覆盖更新（下一步），届时整条链路无人值守全自动。

## 三、任务 3：简历项目经历（初稿）

### 简历条目（STAR 版）

**企业微信知识库智能问答助手（Dify + LangBot + RAG 优化）**  ｜个人项目 ｜ 2026.09 –

- **背景与目标**：针对团队文档分散、重复性问答消耗人力的问题，基于自建 Dify 平台搭建 RAG 知识库问答机器人，通过 LangBot 以 WebSocket 长连接方式接入企业微信，实现零公网服务器成本的群聊/单聊智能问答。
- **部署与工程**：使用 Docker Compose 私有化部署 Dify 全栈（API/Web/PostgreSQL/Redis/Weaviate/Nginx 等 15 个服务）与 LangBot 消息网关，实现零公网服务器成本的本机端到端跑通；独立排查并解决 DNS 污染导致的私有镜像仓库拉取失败（改用可达源拉取 + tag 重命名恢复镜像名）、Windows 下容器卷挂载兼容导致沙箱不可用（配置化降级）等问题；打通"IM 机器人 → LangBot → Dify 应用 API"调用链路，完成流式输出、Markdown 渲染与会话隔离联调。
- **RAG 效果优化**：构建【50】条真实问答评测集，针对基线检索命中不足问题进行三轮优化——① 由通用分块改为父子分块/结构化分块；② 引入混合检索（向量+全文）+ bge-reranker 重排序；③ 提示词工程（答案接地、拒答约束、多轮问题改写）。问答准确率由【72%】提升至【91%】，平均响应【3.2s】。
- **知识库自动化**：设计并落地"计划任务 → 批处理调度 → Python 爬虫 → 结构化 Markdown"的知识库素材自动更新管道（每周一自动抓取 GitHub 周榜 Top10 与 README 摘要，产出 11 篇入库文档并记录运行日志），通过 ASCII 调度层 + Python 运行时定位解决 Windows cmd 中文编码兼容问题；下一步接入 Dify 知识库 API 实现覆盖式自动入库，形成端到端无人值守的周更知识管道。
- **成果**：项目在【个人/团队】范围内上线使用，累计服务问答【N】次，沉淀了可复用的"IM 机器人 + LLMOps 平台"私有化落地方案。

### 面试高频追问预案

1. 为什么选 WebSocket 长连接而不是回调 URL？（部署成本、无公网依赖、企微智能机器人 API 模式特性）
2. 父子分块为什么有效？（子块小→语义聚焦召回准；父块大→上下文完整，缓解碎片化）
3. Rerank 为什么能提升准确率、代价是什么？（双塔召回快但粗 vs 交叉编码器精但慢，只在 TopK 候选上重排；代价是延迟与 API 成本）
4. 评测怎么做的？如何避免"自己改自己判"？（固定测试集、LLM-as-judge + 人工抽检、单变量对照）
5. 文档更新时旧切片怎么处理？（Dify 按文档 ID 覆盖更新/删除重建，防止新旧版本共存互相污染检索）
6. 机器人答非所问/幻觉怎么排查？（查 Dify 日志的召回段：是没检到、检错、还是模型没遵循上下文——三种归因对应不同优化动作）
